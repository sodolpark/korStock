# KRX와 키움증권 REST API 기반 자동매매 구현 계획

작성일: 2026-10-08 · 시간대: Asia/Seoul · 계획 버전: 1.0

후속 구현: [프로젝트 실행 안내](../README.md) · [단계별 구현/검증 상태](../reports/Implementation_Status.md). 아래 계획의 개발 항목은 코드로 구현했으며, 실제 계좌 연결·시장 데이터 수집·20거래일 관찰·실거래 완료 조건은 해당 상태 문서에서 별도로 관리한다.

KRX 보통주 현물을 대상으로 키움증권 REST API와 WebSocket을 연결하여, 종목 탐색 → 하방 위험 배제 → 눌림 안정화 확인 → 매수 체결 우위 진입 → 보유 및 청산을 자동화한다. 먼저 원시 체결·호가 수집기와 동일 데이터를 다시 실행하는 재생 엔진을 만들고, 전략 검증과 주문 연동 검증을 거쳐 제한된 실거래 후보를 완성한다.

개발 기준은 [연구 요약](../0_Research/Korean_Stock_Strategy_Reconstruction.md)과 [상세 구현 명세](../0_Research/Korean_Stock_Strategy_Reconstruction.html)다. 원본의 미공개 진입 산식은 그대로 복제할 수 없으므로 상세 명세의 `research_v1`을 구현 대상으로 삼는다. 확인된 원본 설정과 새로 정한 운영 규칙은 별도 프로필로 보존한다.

이 계획의 산출물은 구현 코드, 수집 데이터, 재현 가능한 검증 결과, 운영 절차다. 현재 요청 범위는 계획서 작성이며, 아래 개발·계좌 연결·주문 실행은 향후 작업이다.

## 1 확정할 구현 범위

| 구분 | 초기 구현 결정 |
|---|---|
| 거래시장 | KRX. 시세·호가·조건검색·주문·계좌 조회의 시장을 명시적으로 일치시킨다. |
| 증권사 | 키움증권 REST API. 실시간 데이터는 해당 서비스의 WebSocket 사용. |
| 상품 | 코스피·코스닥 보통주 현물 매수 후 매도. 신용·미수·공매도 제외. |
| 개발 환경 | 현재 Windows 환경에서 시작하고, 실행 코드는 Linux에서도 동작하도록 구성. |
| 초기 감시 규모 | 30종목에서 시작하여 측정 후 50종목까지 확장. 보유·미체결 종목 우선 유지. |
| 전략 시각 | 일반 거래일 신규 진입 09:02 이상 14:50 미만, 15:19부터 청산 시작. 특별 개장일은 거래일별 일정 적용. |
| 동시 보유 | 연구·모의 프로필 최대 3종목. 최초 실거래 검증은 최대 1종목·1주 이내. |
| 주문 | 기본은 체결 가능한 최우선 상대 호가에 지정가 제출. 가격 상한·미체결·취소 처리를 함께 구현. |
| 실행 판단 | 고정된 수식과 상태 전이. 실시간 주문 경로에서 LLM 호출이나 설정 자동 변경 없음. |
| 후속 범위 | NXT·SOR, 장전·시간외, ATR, 미공개 상한가 알고리즘, 추가매수, 웹 대시보드는 기본 버전 검증 후 검토. |

15:19는 이 전략의 청산 시작 설정이며 체결 보장 시간이 아니다. 일반 거래일 KRX 종가 단일가 구간은 15:20~15:30이므로, 마감 정책은 잔고·미체결 확인까지 포함한다. [KRX 제도 안내](https://regulation.krx.co.kr/contents/RGL/03/03010409/RGL03010409.jsp)

## 2 연구 근거와 구현 규칙 연결

| 연구 항목 | 근거 수준 | 구현 방침 |
|---|---|---|
| 여섯 표시 점수의 합 | 64행 중 63행이 반올림 범위에서 일치 | 산술 회귀 검증과 표시용으로 보존. 미공개 원시 산식에 임의로 100점 진입 기준을 붙이지 않는다. |
| 수익 고점의 80% 보호 | 2.95% × 0.8 = 2.36%가 기록과 일치 | 핵심 청산 모듈로 구현. |
| 고점 수익 2%에서 활성화 | 연구 가설 | `research_v1`에서 채택. 최소 수익 보장값으로 해석하지 않는다. |
| 추세와 불균형의 AND | 설정과 거래 사유가 지지 | 구조는 유지하되, 추세를 bp/분으로 새로 정의하고 기준 0 사용. |
| 7초 3회 확인 | 시간 의미 미확정 | 연속 7초 구간 3개인 21초로 명세 고정. |
| 20초 후 재진입 | 실제 기록과 일치하는 간격 | 완전 청산·미체결 없음 확인 후 20초와 필터 재통과 요구. 원본의 고정 쿨다운으로 단정하지 않는다. |
| 09:00:28 진입 | 거래표에서 확인 | 개장 예외를 만들지 않고 초기 버전은 09:02 이후 데이터 준비 완료 시 시작. |
| 원본 손절 OFF | 설정에서 확인 | 근거 프로필에는 OFF 보존. 운영 프로필은 제안 손실한도 ON. |
| 15:20 청산 기록 | 거래표에서 확인 | 근거 프로필에 보존. 운영 프로필은 15:19부터 청산. |
| 진입 필터·가중 5호가·계좌 한도 | 상세 명세의 제안 | 검증 전 시작값으로 구현하고 버전별 결과를 분리. |

프로필은 `evidence_ui`, `evidence_trade`, `research_v1`, `live_candidate`로 분리한다. 앞의 두 프로필은 근거 비교 전용이고, `live_candidate`는 검증 통과 설정·비용·코드 버전을 동결한 결과다. 원본과 다른 동작을 원본 재현 성과로 보고하지 않는다.

## 3 시스템 구조와 개발 도구

Python 3.12를 초기 개발 기준으로 제안한다. 비동기 통신은 `asyncio`, REST는 `httpx`, 실시간 연결은 `websockets`, 설정·이벤트 검증은 `pydantic`, 테스트는 `pytest`를 사용한다. 실제 착수 시 호환 버전을 확인하여 의존성 잠금 파일로 고정한다.

주문·체결·설정·체크포인트는 SQLite에 트랜잭션으로 기록한다. 고빈도 원시 이벤트는 순차 로그에 기록하고 Parquet로 변환하며, 분석은 DuckDB로 수행한다. 데이터 변환과 무거운 분석은 주문 처리 루프 밖에서 실행한다.

| 구성요소 | 책임 | 주요 산출물 |
|---|---|---|
| BrokerAdapter | 인증, REST, WebSocket, KRX 코드 매핑, 호출 제한 | 증권사와 내부 모델을 분리하는 인터페이스 |
| UniverseManager | 후보 탐색, 구독 할당, 편입·이탈, 준비 상태 | 당시 후보 목록과 선정 사유 |
| MarketDataRecorder | 원본 보존, 정규화, 시간·시장·품질 검사 | 재생 가능한 체결·호가·시장 상태 |
| FeatureEngine | 1초·5초 집계, 체결강도, 불균형, 추세 | 원시 지표와 데이터 유효성 |
| StrategyEngine | 진입 단계와 독립 청산 타이머 | 설명 가능한 진입·청산 의도 |
| RiskManager | 주문 전 노출·손실·수량 검사, 계좌 중단 | 허용 수량과 차단 사유 |
| OrderManager | 주문 상태, 부분체결, 취소 경합, 중복 방지 | 주문 원장과 실제 포지션 |
| Reconciler | 미체결·체결·잔고 조회 결과와 내부 원장 대조 | 재접속·재시작 복구 결과 |
| ReplayEngine | 저장 순서대로 이벤트·타이머 재실행 | 신호 일치 검증과 체결 모의 결과 |
| Reporter | 수집 품질, 주문 이상, 일일 성과, 운영 상태 | 일일 보고서와 로컬 운영 화면 |

초기 실행은 단일 서비스로 구성하되 계좌 상태 변경은 하나의 직렬 처리 경로로 제한한다. 데이터 수신·저장·계산을 논리적으로 분리하고, 큐가 밀리면 오래된 데이터로 신규 주문을 계속 내지 않도록 차단한다. 계좌당 실행 잠금으로 프로그램 중복 기동을 방지한다.

향후 생성할 코드 구조는 다음과 같다. 현재 연구 폴더와 계획 폴더는 그대로 유지한다.

## 4 키움 API 연결 명세

### 4.1 환경과 호출 정책

2026-10-08에 확인한 공식 안내는 국내주식 실전 주문 초당 5회, 조회 초당 5회, 계좌별 세션 1개, 실시간 시세 200종목, 국내주식 실시간 조건검색 10건이다. 조건검색 결과는 최대 100종목이며 모의투자에는 TR별 초당 1회 제한을 안내한다. 이 수치를 설정으로 관리하고, 개발 착수 시 실제 계정에서 적용 범위를 확인한다. [키움 서비스 안내](https://openapi.kiwoom.com/intro?dummyVal=0)

| 연결 | 실전 | 모의 |
|---|---|---|
| REST 기본 주소 | `https://api.kiwoom.com` | `https://mockapi.kiwoom.com` |
| WebSocket 기본 주소 | `wss://api.kiwoom.com:10000` | `wss://mockapi.kiwoom.com:10000` |
| WebSocket 경로 | `/api/websocket` | `/api/websocket` |
| 매매시장 설정 | KRX 지정 | 공식 안내상 KRX 지원 |

주소는 현재 [실시간 체결 상세 명세](https://openapi.kiwoom.com/guide/apiGuideContents/14/0B)와 [주문 상세 명세](https://openapi.kiwoom.com/guide/apiGuideContents/13/kt10000)를 기준으로 한다. 예제·튜토리얼과 경로가 다르면 상세 명세와 연결 시험 결과를 대조하여 확정한다.

주문·조회 제한기를 분리하고 동시에 호출이 몰리지 않게 간격을 둔다. 취소·위험 축소 주문을 신규 매수보다 우선하고, 미체결·잔고 대사 조회를 순위 조회보다 우선한다. 일반 조회는 제한적 재시도가 가능하지만, 주문·정정·취소 응답이 불명확하면 실제 상태를 먼저 확인한다.

### 4.2 기능별 연결 대상

| 용도 | API 또는 실시간 항목 | 구현 포인트 |
|---|---|---|
| 인증 | `au10001`, `au10002` | 만료 시각 관리, 토큰·앱키·시크릿 로그 제거 |
| 후보 순위 | `ka10032` 거래대금상위 | REST `/api/dostk/rkinfo`, `stex_tp=1`로 KRX 지정 |
| 조건검색 | `ka10171`~`ka10174` | 목록·일반·실시간·해제. WebSocket 사용, 실시간 요청 `stex_tp=K` |
| 체결 | `0B` 주식체결 | 거래량 부호, 체결 시각·가격·누적량, 거래소 구분 수신 |
| 호가 | `0D` 주식호가잔량 | 매수·매도 1~10호가의 가격·수량 수신 |
| 주문 통보 | `00` 주문체결 | 주문번호·원주문번호·체결번호·미체결수량·상태 |
| 잔고 통보 | `04` 잔고 | 체결 원장과 교차 검증. 중복으로 보유 수량을 더하지 않음 |
| 시장 상태 | `0s` 장시작시간, `1h` VI발동/해제 | 세션·VI 상태와 타이머 연결 |
| 주문 | `kt10000`~`kt10003` | 매수·매도·정정·취소, REST `/api/dostk/ordr` |
| 계좌 대사 | `ka10075`, `ka10076`, `kt00018`, `kt00001` | 미체결·체결·잔고·예수금 및 연속조회 처리 |
| 종목 상태 | `ka10099`, `ka10100`, `ka10001`, `ka10054` | 종목 목록·거래 가능 상태·가격제한·VI 조회에 필요한 필드 확인 |

위 항목은 [공식 API 목록](https://openapi.kiwoom.com/m/guide/apiguide?dummyVal=0)을 기준으로 연결할 대상이다. 개별 API의 모의 지원 범위와 모든 응답 필드는 첫 연결 단계에서 계약 테스트로 확정한다.

KRX 표기 방식은 API마다 다르다. 주문은 `dmst_stex_tp=KRX`, 순위는 `stex_tp=1`, 조건검색은 `stex_tp=K`를 사용한다. 실시간 구독은 KRX 종목코드를 사용하고 `_NX`, `_AL`을 임의로 제거하여 KRX 데이터로 받아들이지 않는다. 조건검색·계좌 응답의 상품 접두어도 API별 규칙에 따라 정규화한다. [순위 명세](https://openapi.kiwoom.com/guide/apiGuideContents/05/ka10032), [조건검색 명세](https://openapi.kiwoom.com/guide/apiGuideContents/15/ka10173), [주문 명세](https://openapi.kiwoom.com/guide/apiGuideContents/13/kt10000)

### 4.3 데이터 해석에서 먼저 검증할 사항

`0B`의 거래량 필드 `15`는 공식 명세상 양수가 매수체결, 음수가 매도체결이다. 수량의 절댓값을 취하기 전에 방향을 추출한다. 가격의 부호와 체결 방향을 혼동하지 않는다. API 체결강도 `228`은 별도로 저장하고, 전략의 최근 20초 체결강도는 원시 체결에서 다시 계산한다. [체결 상세 명세](https://openapi.kiwoom.com/guide/apiGuideContents/14/0B)

`0D`는 10호가를 모두 저장한 뒤 전략에서 5호가를 선택한다. `00`의 체결량·단위체결량·미체결량이 각 상황에서 어떻게 변하는지 검증하고, 하나의 체결을 통보와 REST 조회에서 중복 반영하지 않는다. [호가 상세 명세](https://openapi.kiwoom.com/guide/apiGuideContents/14/0D), [주문체결 상세 명세](https://openapi.kiwoom.com/guide/apiGuideContents/14/00)

## 5 후보 탐색과 데이터 수집

### 5.1 후보 선정과 구독 유지

첫 후보 탐색은 거래대금 순위 조회로 시작한다. 30초 주기로 갱신하는 것을 초기 운영 제안값으로 두고, 계좌 조회 예산이 부족하면 갱신을 늦춘다. 조건검색은 기존 HTS 조건식의 준비 여부와 API 지원을 확인한 뒤 보조 후보 공급원으로 추가한다. 계좌나 조건식이 없어도 고정 관심종목과 저장 데이터로 엔진 개발을 진행할 수 있다.

보통주·정상 거래 상태를 먼저 필터링한다. ETF·ETN, 신규상장 첫날, 거래정지, 단기과열·단일가 대상은 제외한다. 종목 상태가 확인되지 않으면 진입 대상에 넣지 않는다.

구독 우선순위는 보유 종목 → 미체결 종목 → 진입 단계 진행 중 종목 → 신규 후보다. 조건검색에서 이탈하거나 순위가 내려가도 보유·미체결 종목은 해제하지 않는다. 초기 총 감시 상한은 30종목이며, 50종목 확장은 수신 품질 검증 뒤 진행한다. 상한에는 보유·미체결 종목도 포함한다.

새 후보는 `WARMING`으로 등록하고 충분한 데이터가 쌓인 뒤 `READY`로 전환한다. 신규 편입 전의 호가를 현재 호가로 소급 채우지 않는다. 가능하면 후보를 최소 360초 유지하되 보유·주문 관리가 필요한 종목을 우선한다. 구독 교체가 잦아 데이터 준비를 반복하지 않도록 편입 사유·구독 기간·제외 사유를 기록한다.

### 5.2 저장할 레코드

| 레코드 | 필수 내용 |
|---|---|
| 공통 이벤트 | 거래일, 종목, 시장, 원본 API 종류, 연결 세대, 수신 순번, 원본 메시지, 스키마 버전 |
| 시간 | 제공되는 거래소 시각, UTC 수신 시각, 프로세스 내 단조 증가 시각. 표시·장 일정은 Asia/Seoul |
| 체결 | 가격, 개별 수량, 매수·매도 주도 방향, 누적량, 체결 조건과 품질 상태 |
| 호가 | 매수·매도 1~10호가 가격·잔량, 호가 발생 시각, 시장 상태 |
| 후보 이력 | 선정 당시 순위·조건, 필터 결과, 구독 시작·종료, 데이터 준비 상태 |
| 주문·체결 | 계좌 별칭, 내부 주문 의도 ID, 주문번호·원주문번호·체결번호, 수량·가격·상태 |
| 신호·설정 | 설정 해시, 코드 버전, 실제 분석창, 지표값, 유효성, 단계 전이, 타이머, 청산 사유 |

계좌 원장과 시세 로그의 영속 기록 위치를 분리한다. 주문 전 내부 의도를 먼저 트랜잭션으로 남기고, 재시작 때 해당 의도와 증권사 상태를 대조한다. 비밀키·인증 헤더는 원본 로그에서도 제거한다.

### 5.3 시간과 데이터 품질

실행과 재생은 수신 순서 및 수신 시점에 이용 가능했던 정보로 판단한다. 동일 초에 여러 체결이 발생하므로 시각·가격·수량이 같다는 이유만으로 체결을 중복 제거하지 않는다. 원천 순번이 제공되지 않으면 로컬 순번은 수신 순서만 나타내며, 거래소 전체 체결의 완전성을 증명하지 않는다.

호가 수신 후 경과 시간이 2초를 넘으면 신규 진입을 막고, 5초를 넘으면 상태 점검·경보를 시작한다. 이는 초기 제안 기준이다. 무거래와 연결 장애는 heartbeat·다른 종목의 수신·시장 상태를 함께 확인하여 구분한다. 단순히 새 호가가 없다는 이유로 연결 장애나 즉시 매도를 확정하지 않는다.

1초 집계에서 호가의 이전 값을 최대 2초까지만 전달한다. 선택 분석창의 유효 표본 비율은 90% 이상을 요구하고, 실제 공백·VI·연결 장애는 별도 기록한다. 거래소 시각이 초 단위라면 밀리초 단위 네트워크 지연을 정밀 측정한 것처럼 보고하지 않는다.

디스크 기록 실패, 큐 초과, 수신 처리 지연이 발생하면 신규 진입을 차단한다. 관측된 유실 구간을 명시하고 해당 구간의 수익성 결과를 정상 데이터와 섞지 않는다. 시세 품질 악화와 무관하게 기존 주문 확인과 위험 축소 경로는 계속 관리한다.

## 6 전략 수식과 상태 전이

### 6.1 지표 정의

상세 연구 명세 8~10절을 기본으로 한다. 아래에서 수익률은 퍼센트 값, 수량·노출 계산의 비율은 소수 비율로 구분한다.

```text
mid = (최우선 매수호가 + 최우선 매도호가) / 2
r_W = 100 × (mid_now / mid_W_seconds_ago - 1)
A_W = 최근 W초 Σ(체결가격 × 체결수량)
E_W = 100 × 최근 W초 매수주도 체결량 / 매도주도 체결량

w = (1.0, 0.8, 0.6, 0.4, 0.2)
B5 = Σ(w_i × 매수잔량_i)
A5 = Σ(w_i × 매도잔량_i)
I5 = (B5 - A5) / (B5 + A5)
I5_10s = 최근 10초 I5의 시간가중 평균
I_W = 최근 분석창 W초 I5의 시간가중 평균

T = 10,000 × OLS기울기(log(mid), 시간축 단위 분)
sigma_pct = 최근 완성 1초 log수익률 60개의 표준편차 × 100
W_target = clip(360 / (1 + 10 × sigma_pct), 120, 360)초
```

분모 0, 비정상·역전 호가, 필수 필드 누락은 유효 지표로 만들지 않는다. 체결 방향 미상 비중은 최근 20초 전체 체결수량 대비로 정의하고, 20% 초과 시 진입을 금지한다. 매도주도 체결량 0도 무한대 체결강도로 매수하지 않는다.

적응창은 10초마다 평가하고 10초 단위로 내림한다. 시작 구간의 모호함을 줄이기 위해 `W_effective = min(W_target, 확보된 연속 구간을 10초 단위로 내린 길이)`로 보완한다. 120초 미만이면 추세 청산은 준비 전이다. 이 보완은 계획에서 정한 구현 규칙이며 로그에 목표창과 실제창을 모두 남긴다. 고정 손절·시간 청산·준비된 수익보호는 장기 지표 준비 여부와 별도로 동작한다.

### 6.2 진입 단계

| 단계 | 통과 조건 | 실패 처리 |
|---|---|---|
| 공통 | 진입 가능 시간, 정상 시장 상태, 준비된 데이터, 최근 60초 거래대금 ≥ 5억원·체결 ≥ 100건, 스프레드 ≤ 2틱이며 mid 대비 ≤ 0.20% | 진입 금지, 사유 저장 |
| 1차 하방 배제 | `r60 ≥ -0.50%`, `r10 ≥ -0.20%`, `I5_10s > -0.70` | 후보 진행 초기화 |
| 2차 안정화 | 완성된 5초 구간 4개의 중간호가 범위 ≤ 마지막 중간호가의 0.60%, 뒤 10초 저점 ≥ 앞 10초 저점 - 1틱, `I5_10s > -0.50` | 준비 상태 유지 또는 180초 만료 |
| 3차 매수 우위 | `E20 ≥ 120`, `A10/(A60/6) ≥ 1.2`, 매수주도 체결가가 직전 완성 5초 구간 체결 고점 + 1틱 이상 | 돌파·가격·필터 유효성 재평가 |
| 주문 직전 | 공통·1차 재확인, 2차 통과 후 30초 이내, 실제 최우선 매도호가 ≤ 돌파 기준 + 2틱, 위험 한도 통과 | 가격 추격 없이 포기 |

5초 구간은 KST 시각의 5초 경계로 고정하고 완성 구간만 사용한다. 구간 내 체결이 없어 돌파 고점이 정의되지 않으면 해당 진입은 보류한다. 가격 구간 경계에서는 종목·거래일의 호가단위를 적용하여 합법적인 다음 호가를 계산한다.

후보 상태는 `WARMING → READY → STAGE1 → STAGE2 → ENTRY_PENDING`으로 관리한다. 최초 1차 통과부터 180초를 초과하면 단계를 만료시킨다. 이후 재평가는 가능하지만 이전 통과 시각을 재사용하지 않는다.

완전 청산 및 관련 미체결 0 이후 20초가 지나야 재진입할 수 있다. 같은 종목 진입은 하루 최대 3회, 연속 손절 2회면 당일 신규 진입을 중단한다. 최초 실제 매수 체결을 1회로 계산하며, 미체결 취소는 진입 횟수에 포함하지 않는다. 보유 중 추가매수는 하지 않는다.

### 6.3 청산 규칙

| 우선순위 | 조건 | 실행 |
|---|---|---|
| P0 | 일일 손실한도·명시적 긴급 청산 요청 | 신규 진입 중단, 미체결 매수 취소, 가능한 보유 수량 위험 축소 |
| P1 | 평균매수가 대비 유효 최우선 매수호가 수익률 ≤ -1.5% | 일반 확인 타이머 없이 청산 의도 생성 |
| P2 | 세션 청산 시작 시각 도달 | 신규 진입 중단, 매수 잔량 취소, 보유 청산·잔고 대사 |
| P3 | 확정 고점 수익 ≥ 2%, 현재 유효 체결 수익이 보호선 아래에서 10초 연속 유지 | 수익 트레일링 청산 |
| P4 | `T < 0 bp/분` AND `I_W < -0.70`이 연속 21초 유지 | 추세·불균형 청산 |

수익 보호선은 `F_new = 0.8 × 확정 고점 수익률`, `F = max(F_previous, F_new)`로 계산한다. 2%에서 활성화되면 최초 보호선은 1.6%가 될 수 있다. 수수료 차감 전 가격수익으로 신호를 계산하고, 계좌 손익과 성과 보고에는 비용을 반영한다.

고점은 원시 고점·확인 중 후보·확정 고점으로 분리한다. 후보 가격의 99.9% 이상을 유효 가격이 10초 유지하면 확정하고, 확인 중 더 높은 체결이 발생해도 기존 타이머를 계속 초기화하지 않는다. 새 고점은 다음 확인 후보로 별도 관리한다. 후보 경계 이탈·VI·데이터 공백이면 확인을 취소하며 확정 보호선은 낮추지 않는다.

상세 연구의 3봉 고점 리셋과 15% 이상치 필터는 원본 산식이 불명확하므로 초기 버전에서 가격만으로 자동 적용하지 않는다. 의심 이벤트 격리·호가 교차 확인을 먼저 구현하고, 실제 급락을 정상 데이터에서 지워 손절을 무력화하지 않는다. 3봉 후보 폐기와 ATR 등은 별도 실험으로 평가한다.

트레일링 10초와 추세 확인 21초는 독립 타이머다. 조건 회복·시세 무효·VI에서는 해당 연속 타이머를 초기화한다. 틱이 없는 시간도 타이머 스케줄러는 동작하되, 오래된 시세로 조건 지속을 인정하지 않는다. 동시 청산 사유는 하나의 주문 의도로 합치고 보조 사유를 모두 기록한다.

## 7 주문 관리와 계좌 위험

### 7.1 주문과 보유 상태

보유 수량과 주문 상태를 별도로 관리한다. 일부 매수만 체결된 상태에서는 보유 위험과 남은 매수 주문이 동시에 존재한다. 포지션의 요약 상태만으로 두 상태를 덮어쓰지 않는다.

```text
주문: CREATED → SENT → ACKNOWLEDGED → PARTIALLY_FILLED → FILLED
                     ↘ REJECTED
          미완료 주문 → CANCEL_PENDING → CANCELED 또는 추가 체결
          응답 불명   → UNKNOWN → 증권사 조회와 대사

계좌 운영: STARTING → RECONCILING → RUNNING
                    ↘ HALTED 또는 EXIT_ONLY
```

내부 주문 의도 ID는 로컬 중복 방지 수단이다. 증권사가 그 ID를 이용한 멱등 주문을 보장한다고 가정하지 않는다. 응답을 받지 못하면 동일 주문을 자동 재전송하지 않고 주문·체결·잔고를 대조한다. 일치 여부가 불명확하면 신규 진입 중단 상태를 유지한다.

체결은 거래일·계좌·주문번호·체결번호로 식별하고, 원주문 연결과 취소·정정 이력을 보존한다. 식별값 누락이나 서로 다른 체결 통보가 충돌하면 수량을 추정하여 덧셈하지 않고 대사로 전환한다. 재접속 조회에서 발견된 누락 체결·외부 거래는 별도 원장 이벤트로 반영한다.

### 7.2 체결과 취소 처리

매수는 가격 상한을 통과한 최우선 매도호가에 지정가로 제출한다. 접수 확인 후 2초 이내 미체결 잔량이 남으면 취소 의도를 생성한다. 이 시간은 재주문 허가가 아니며, 취소 확인 전에는 대체 매수 주문을 내지 않는다.

부분체결은 첫 체결부터 평균매수가·고점·손실 관리에 반영한다. 청산 조건이 생기면 미체결 매수 취소를 우선 요청하면서 이미 보유한 수량의 위험도 관리한다. 취소 응답을 무한히 기다리느라 체결된 보유분 청산을 멈추지 않는다. 취소 중 추가 매수가 체결되면 청산 의도에 추가 수량을 반영한다.

매도 가능 수량은 실제 보유량에서 유효한 기존 매도 주문 잔량을 뺀 값이다. 일반 청산은 최우선 매수호가 지정가로 시작하고 2초 단위로 진행 상태를 평가한다. 취소 확인 또는 검증된 정정 결과에 따라 잔량만 재가격한다. 호출 한도 때문에 평가 시각과 API 호출 시각이 달라질 수 있으며 둘 다 기록한다.

긴급 청산 주문 종류는 KRX 세션·지원 주문을 확인한 뒤 지정가 또는 시장가로 사전 설정한다. VI·거래정지·잔량 부재·가격제한에서는 체결되지 않을 수 있으므로 청산 의도를 유지하고 상태를 보고한다.

### 7.3 수량과 손실한도

아래는 연구 명세의 검증 전 시작값이며, 현재 사용자의 계좌 자금으로 확정한 비중이 아니다.

```text
E0 = 당일 시작 순자산
거래당 계획 위험 = E0 × 0.002
손절 거리 d = 0.015
c = 계정별 왕복 비용률 + 스트레스 슬리피지율

q_risk = floor(E0 × 0.002 / (진입가격 × (d + c)))
q_name = floor(E0 × 0.20 / 진입가격)
q_liquidity = floor(최근 60초 체결수량 × 0.01)
q_portfolio = floor(전체 50% 노출 상한의 남은 금액 / 진입가격)
q = max(0, min(q_risk, q_name, q_liquidity, q_portfolio, 주문가능수량))

일일 중단 = 비용 포함 실현손익 + 청산 예상 비용 포함 평가손익 ≤ -E0 × 0.01
```

노출과 주문가능금액에는 체결된 보유뿐 아니라 미체결 매수의 예약 금액을 포함한다. 동시 신호가 예산을 중복 사용하지 않도록 위험 검사·예약·주문 의도 저장을 직렬화한다. 수량 0이면 거래하지 않는다. 최초 실거래 모드의 1주 제한도 계산 결과보다 수량을 늘리는 예외로 사용하지 않는다.

손실 중단 상태는 당일 지속하고 재시작으로 해제하지 않는다. 입출금·외부 거래를 손익과 분리하며, 전용 계좌 또는 계좌 내 다른 거래를 식별할 수 있는 운영 범위를 정한다. 상관관계가 높은 종목의 동시 진입 효과는 평가 항목으로 남기고, 테마 정보가 없는데 테마 노출 제한을 검증했다고 보고하지 않는다.

### 7.4 재시작과 마감

재시작 시 저장 원장 복구 → 미체결 → 당일 체결 → 잔고·예수금 대사 → 구독 복구 → 데이터 준비 순으로 진행한다. 재시작 후 단조 증가 시계는 새로 시작하므로 이전 확인 타이머를 이어붙이지 않는다. 확정 고점·보호선·당일 진입 횟수·중단 상태는 영속 상태에서 복원한다.

15:19부터 신규 진입을 차단하고, 15:20 전 청산 완료를 목표로 한다. 15:20 이후 남은 주문은 종가 단일가 정책으로 전환하여 감시하며 접속매매 체결로 모의 처리하지 않는다. 정규장 종료 후 잔고나 미체결이 남으면 예외 상태와 인계 절차를 기록한다. 자동으로 NXT로 옮기거나 잔고를 0으로 간주하지 않는다.

### 8.2 성과 검증

체결 모형은 신호 이후 실제 지연을 적용한 다음 호가에서 체결을 평가한다. 매수는 매도호가, 매도는 매수호가의 깊이와 수량을 사용하고 미체결·부분체결·취소 경합을 반영한다. 지정가가 닿았다는 이유만으로 전량 체결하지 않는다. 호가 스냅샷으로 알 수 없는 대기열 순서는 보수적 시나리오로 평가한다.

수수료·세금은 계정·상품·거래일 기준으로 입력한다. 연구 기록을 설명한 약 0.23% 비용 모형을 현재 실제 비용으로 고정하지 않는다. 원시 호가 없는 분봉 백테스트는 이 전략의 불균형·체결 성과 검증을 대체하지 못한다.

개발·검증·최종 보류 데이터는 날짜 순으로 60%·20%·20% 분리한다. 360초 분석창과 보유 구간이 경계를 넘지 않게 처리하고 종목별 편중도 함께 점검한다. 후보 편입 당시 관측 가능한 데이터만 사용하며, 나중에 급등한 종목만 골라 평가하지 않는다. 보류 구간을 본 뒤 설정을 바꾸면 새 보류 구간이 필요하다.

기본 실험은 손실한도·시간 청산 → 수익 트레일링 추가 → 추세·불균형 추가 → 고점·하방 확인 추가 순서로 진행한다. 적응창의 효과도 고정창과 따로 비교한다. 각 실험의 설정·시도 횟수·데이터 범위를 저장한다.

최종 보고서는 거래당 순기대수익, 계좌 MDD, 최악 일손실, 승률·평균손익, MFE·MAE, 체결률·슬리피지, 재진입 비용, 종목·시간대·장세별 결과를 포함한다. 실제 체결이 없는 `shadow` 결과는 예상 성과로 표시한다.

실거래 후보 전환에는 비용 차감 기대값의 날짜 블록 bootstrap 95% 하한이 양수인지 확인한다. MDD 허용값은 자금·기간에 맞춰 보류 구간 열람 전에 정한다. 표본이 부족하거나 한도값이 미정이면 성과 통과 판정을 유보한다. 비용 2배·불리한 1~2틱·실측 상위 지연 시나리오에서도 사전 손실 한도를 만족하는지 별도로 검사한다.

P2 수집은 완성 즉시 누적하고 P3~P6 개발 중에도 유지한다. 확보 데이터가 부족하면 개발 완료와 성과 검증 완료를 분리한다. 20거래일의 무주문 관찰만으로 여러 달의 분리 검증을 대체하지 않는다. 실시간 계정 접근이 준비되지 않아도 P0·프로젝트 골격·가상 이벤트 검증은 진행할 수 있다.

개발 일정은 단계 완료 조건으로 관리한다. API 계정·원시 데이터·검증 기간의 확보 시점이 정해지기 전에는 실거래 시작일을 고정하지 않는다.

| 원장과 실제 잔고 불일치 | 신규 진입 중지, 원인·외부 거래 조사 | 차이 해소 및 기록 |
| 일일 손실한도 도달 | 당일 신규 진입 중단, 취소·위험 축소 | 다음 거래일 시작 절차와 잔여 위험 확인 |
| 저장 실패·디스크 부족 | 신규 진입 중지, 기존 보유·주문 관리 우선 | 저장 복구·영속 상태·대사 확인 |
| 마감 후 잔량 | 예외 보고·보유 위험 인계 | 실제 잔량 해소 또는 다음 세션 관리 계획 |

API 키는 환경변수 또는 OS 비밀정보 저장소로 공급하며 문서·설정 샘플에 실제 값을 쓰지 않는다. 주문 원장과 설정은 백업하고, 시세 보존 기간은 수집 1일의 실제 용량을 측정한 뒤 정한다. 시험에는 시장 데이터 원본 또는 비밀정보를 제거한 응답만 사용한다.

## 11 외부 준비 사항과 미확정 항목

| 항목 | 필요한 시점 | 처리 방침 |
|---|---|---|
| 키움 계좌·HTS ID·REST API 신청 | P1 실제 연결 | 실전·모의 권한과 접속 IP 정책 확인. 비밀값은 로컬 보관. |
| 조건검색 식 | 조건검색 추가 시 | 저장된 식과 편입·이탈 동작 확인. 초기에는 순위 조회로 진행 가능. |
| 과거 틱·10호가·후보 이력 | P6 성과 검증 | 제공 범위 확인 또는 P2부터 직접 수집. 체결 이력만으로 호가를 복원하지 않음. |
| 모의 부분체결·VI·정정 동작 | P5 | 모의에서 재현할 수 없는 사례는 로컬 장애 주입으로 검증하고 한계 표시. |
| 현재 수수료·세금·호가단위·특별 일정 | P0 및 실거래 전 | 계정·종목·거래일별 공식 조건을 입력하고 적용일 보존. |
| 실전 자금·계좌 혼용·허용 MDD | 보류 성과 평가 전 | 운영 한도를 확정하고 검증 결과를 본 뒤 유리하게 바꾸지 않음. |
| 원본 진입 수식·추세 단위·고점 리셋 | 원본 재현 확장 시 | 확보 전에는 evidence 프로필의 미확정 항목 유지. 기본 개발을 막지 않음. |
| 동일 계정 내 다른 API 프로그램 | P1 운영 설정 | 세션·호출 예산 충돌 확인, 중복 기동·외부 주문 탐지. |

## 12 첫 개발 작업 목록

- [ ] P0 설정 스키마에 시장·모드·프로필·시간대·단위·비용 필수값 정의
- [ ] 연구 HTML의 점수 64행·거래 3건을 회귀 자료로 정리
- [ ] API별 KRX 표기와 원시 필드 매핑을 계약 테스트 자료로 고정
- [ ] Python 패키지·의존성 잠금·비밀정보 제외 규칙 구성
- [ ] 실제 주문 기능이 없는 REST 조회 및 WebSocket 수집 실행 모드 구현
- [ ] 체결 방향·10호가·수신 시각·원본 메시지 저장 구현
- [ ] 재연결·구독 복구·거래일 종료 시 저장 검증 구현
- [ ] 고정 관심종목 → 순위 기반 30종목 순서로 수집 품질 점검
- [ ] 저장 이벤트를 가상 시계로 재생하는 최소 엔진 구현
- [ ] 수익 고점 2.95% → 보호선 2.36%와 독립 확인 타이머 검증

첫 인도 목표는 P2까지의 데이터 수집기와 재생 가능한 원본 파일이다. 원시 데이터 확보가 이후 진입 산식 검증·체결 모의·실시간 대조의 공통 선행 조건이다.
